# 자산 역할/중요도 분류

자산탐지(1단계) 직후, 퍼징 순서를 정하기 전에 수행. 도메인명/기술핑거프린트만으로 "이게 뭐하는 시스템일지" 1차 추정해서, 제한된 시간 안에 고위험 자산부터 파고들 수 있게 함.

## 원칙

블랙박스 초기엔 시스템 내부를 모르니 **naming + 기술스택 핑거프린트**가 유일한 단서. 정확도는 완벽하지 않지만, "전수조사 vs 우선순위 기반 조사"의 차이를 만듦 — 특히 계약 기간이 짧을수록 이 필터링의 가치가 큼.

## 도메인명 기반 추정 (일반 패턴)

| 도메인/서브도메인에 포함된 단어 | 추정 역할 | 중요도 |
|---|---|---|
| `admin`, `manage`, `console`, `backoffice` | 관리자 콘솔 | 높음 (권한상승 시 전체 장악 가능) |
| `api`, `gateway`, `svc` | API 게이트웨이/백엔드 서비스 | 높음 (인증/데이터 흐름 집중) |
| `vpn`, `remote`, `citrix` | 원격접속 게이트웨이 | 매우높음 (내부망 진입점) |
| `pay`, `billing`, `finance`, `erp` | 결제/재무 시스템 | 매우높음 (금전적 영향 직접적) |
| `hr`, `member`, `mypage`, `customer` | 개인정보 처리 시스템 | 높음 (PII 노출 위험) |
| `dev`, `stg`, `staging`, `uat`, `test`, `qa` | 개발/스테이징 환경 | 중간~높음 (보안설정 느슨한 경우 많아 오히려 진입점으로 유용) |
| `cdn`, `static`, `assets`, `img` | 정적 콘텐츠 전용 | 낮음 (직접적 위험 적음, 단 S3 버킷 오설정 등은 확인) |
| `mail`, `smtp`, `webmail` | 메일 시스템 | 중간 (피싱/정보수집 연계 가능) |
| `iot`, `device`, `sensor` | IoT/디바이스 제어 | 높음 (물리적 영향 가능성) |

## 업종별 벤더 제품 시그니처 (호텔 예시)

호텔/숙박업 대상이면 아래 벤더명이 도메인/기술스택에서 확인될 수 있음:

| 시그니처 | 제품 | 역할 | 중요도 |
|---|---|---|---|
| `opera`, `ohip`, `oracle-hospitality` | Oracle OPERA Cloud (PMS) | 예약/객실관리/결제 정보 핵심 시스템 | 매우높음 (고객 PII+결제정보 집중, 실제 파르나스호텔 케이스에서도 핵심 공격면) |
| `micros`, `simphony` | Oracle MICROS Simphony (POS) | 매장/레스토랑 결제단말 연동 | 매우높음 (카드정보 처리) |
| `iqware`, `protel`, `cloudbeds` | 타 PMS 솔루션 | OPERA와 동일한 역할군 | 매우높음 |
| `kiosk`, `checkin`, `selfcheckin` | 무인 체크인 키오스크 백엔드 | 물리적 접근 연계 가능 (키오스크 이스케이프와 결합 시 심각) | 높음 |
| `smartroom`, `roomcontrol`, `iot` | 스마트룸 제어 시스템 | 객실 IoT 제어 (조명/도어락 등) | 높음 (물리보안 직결) |
| `ota`, `booking`, `channel` | OTA 연동(부킹닷컴 등 채널매니저) | 외부 연동 엔드포인트, 인증토큰 관리 | 높음 |

이 표는 계속 확장 가능 — 업종이 다르면(금융/공공 등) 그 업종의 흔한 벤더 제품명으로 별도 표 구성. 예: 금융이면 `fds`(이상거래탐지), `openbanking`, `esb` 등.

## 기술스택 핑거프린트와 결합 판단

`asset-discovery.md`에서 `httpx -tech-detect`로 확보한 정보와 naming을 교차 확인:

```bash
# tech-detect 결과에서 특정 벤더/미들웨어 확인
cat alive_hosts.txt | grep -i "oracle\|jeus\|weblogic\|tomcat"
```

- 도메인명은 일반적인데(`www`, `service01`) 기술스택에서 특이 미들웨어가 잡히면 → naming보다 기술스택 신호를 우선
- 반대로 naming은 특징적인데(`opera-api`) tech-detect가 아무것도 안 잡으면(WAF가 헤더 감추는 경우) → naming 신호로 우선순위 유지, 수동 확인으로 검증

## 중요도 산정 후 처리

```
자산목록 + 추정역할 + 중요도(상/중/하) 표 작성
→ "상" 등급부터 3단계(포트확인)~4단계(퍼징) 우선 진행
→ "하" 등급은 시간 남으면 진행, 안 남으면 목록만 보고서에 기록(미점검 사유 명시)
```

이 표 자체가 보고서의 "자산 인벤토리 및 위험도 평가" 섹션 초안으로 바로 활용 가능 — 나중에 다시 정리할 필요 없이 이 단계에서 산출물 겸용으로 만들 것.

## 주의사항 — 추정이지 확정 아님

- naming/기술스택 기반 추정은 오탐 있을 수 있음 (`admin`이 들어가도 실제론 마케팅팀 내부용 소개 페이지일 수 있음) — 우선순위 정하는 용도로만 쓰고, 실제 취약점 판단은 반드시 접속 후 확인
- 고객사에 특수 내부 네이밍 규칙이 있을 수 있음 — 초반 몇 개 자산 확인하면서 그 조직 특유의 네이밍 패턴을 발견하면 이 표에 실시간으로 추가해나갈 것

## 산출물을 Excel로 저장

이 단계 표(자산목록+추정역할+중요도)는 임시 마크다운으로만 남기지 말고, `scripts/export_asset_inventory.py`로 xlsx 파일까지 만들어서 저장하는 것을 기본 산출물로 삼는다. 이유: 보고서 작성 시 그대로 첨부 가능하고, 고객사와 공유하기도 쉬움.

```bash
# 입력 CSV 컬럼: subdomain,resolved_to,source,role_guess,importance,notes
python scripts/export_asset_inventory.py assets.csv asset_inventory.xlsx --target <대상도메인/회사명>
```

- `resolved_to`: IP 또는 CNAME 체인 (DNS 응답 없으면 "DNS 응답 없음" 등으로 명시 — 내부망 전용 추정 근거가 됨)
- `source`: crtsh / subfinder / amass / dns-bruteforce 등 확보 출처 (교차검증 여부 추적용)
- `importance`가 상/중/하이면 자동으로 행 색상 강조됨 (상=빨강, 중=노랑, 하=초록)
- 저장 위치는 프로젝트 성격과 섞이지 않는 별도 결과 폴더에 저장할 것 (예: 모의해킹 전용 폴더) — 스터디/문서 폴더 등과 절대 혼용하지 말 것
