# 훅 병합 원칙 (다중 방어로직 동시 대응 시)

금융앱처럼 SSL/루팅/에뮬레이터/무결성이 동시에 걸린 경우, 각 카테고리 문서의 스크립트를 그냥 이어붙이면 안 됨. Frida/JS는 **같은 대상(같은 클래스의 같은 메서드)에 `implementation`을 두 번 할당하면 마지막 것만 살아남고 앞의 훅은 조용히 사라짐** — 에러도 안 남기 때문에 알아채기 어려운 실패 원인이 됨.

## 원칙

1. **같은 Java 메서드는 스크립트 전체에서 딱 한 번만 override**
   - 예: `File.exists()`는 루팅탐지(su 경로)와 에뮬레이터탐지(qemu 경로)에서 둘 다 필요할 수 있는데, 각자 override하면 안 되고 `file-exists-guard.js`처럼 **경로 블록리스트를 하나로 합쳐서 단일 override**로 처리
   - 같은 원칙이 적용될 만한 다른 후보: `Runtime.exec()` (루팅탐지의 getprop 체크 + 다른 이유로 exec 체크하는 경우), `String.contains()` (anti-frida의 TracerPid 체크 + 다른 문자열 매칭)

2. **원본 동작을 항상 fallback으로 유지**
   - 블록리스트에 없는 케이스는 반드시 `return this.exists()` (원본 호출)으로 넘겨야 함. 무조건 true/false 고정하면 앱의 정상 파일 접근 로직까지 깨져서 다른 곳에서 크래시남

3. **스크립트 조립 순서**
   - 2단계 판정에서 필요하다고 나온 모듈들을 리스트업
   - 겹치는 Java 메서드가 있는지 먼저 확인 (`file-exists-guard.js` 같은 통합 버전이 이미 있으면 그거 사용)
   - 안 겹치는 모듈들(예: `CertificatePinner.check`, `RootBeer.isRooted`)은 각자 템플릿 그대로 이어붙여도 무방 — 다른 클래스/메서드라 충돌 없음
   - anti-frida 관련 훅은 항상 스크립트 최상단에 배치 (SKILL.md 3단계 훅 순서 원칙과 동일)

4. **하나로 합친 후 로드 시점에 각 훅의 로그를 전부 확인**
   - `console.log("[+] Hooked: ...")`가 기대한 개수만큼 다 찍히는지 확인. 일부만 찍히면 병합 과정에서 덮어쓰기가 발생했다는 신호

## 현재 통합되어 있는 것

- `file-exists-guard.js`: 루팅탐지(su 경로) + 에뮬레이터탐지(qemu 경로) 통합. 새 카테고리에서 또 `File.exists`가 필요해지면 이 파일의 블록리스트에 추가하고, 개별 문서에서 별도 override 만들지 말 것.

새로운 겹침이 발견되면(예: `Runtime.exec` 이중 사용 등) 같은 패턴으로 통합 스크립트를 만들고 이 문서에 등록할 것.
